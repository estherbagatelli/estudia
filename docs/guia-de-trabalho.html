1.Preparar a sua máquina

Uma vez só, no começo. Leva uns 15 minutos.

Passo 1 — Aceitar o convite

Chegou um e-mail do GitHub convidando você para o repositório. Aceite — sem isso você não consegue enviar o seu trabalho.

Passo 2 — Baixar o projeto

git clone https://github.com/estherbagatelli/estudia.git
cd estudia
npm install

O npm install demora alguns minutos na primeira vez. É normal.

Passo 3 — As chaves do banco

Peça as chaves no grupo, crie um arquivo chamado .env na pasta do projeto e cole o que te mandarem. O passo a passo detalhado está no arquivo SETUP.md do repositório.

O projeto não abre sem isso
Se você rodar sem o .env, aparece uma tela de erro pedindo as chaves. Não é bug — é só a configuração faltando.

Passo 4 — Rodar

npm run dev

Abra http://localhost:3000 no navegador, crie uma conta com o seu e-mail e entre.

Sua conta vai começar vazia — e é de propósito
Uma das entregas da Fase 2 são as mensagens de "você ainda não adicionou nada". Se a conta já nascesse cheia, essas telas nunca apareceriam.

2.As extensões do VS Code

Ao abrir o projeto, o VS Code mostra um aviso perguntando se você quer instalar as extensões recomendadas. Clique em sim. Se o aviso não aparecer, aperte Ctrl+Shift+X e digite @recommended.

Antes de tudo: o que é uma extensão?

É um complemento que você instala no seu editor, não no projeto. Ela muda o jeito que o VS Code te ajuda enquanto você escreve — e só na sua máquina.

Extensão do VS Code Biblioteca do projeto
Onde mora só no seu computador dentro do projeto, no package.json
Quem é afetado só você as seis pessoas
Precisa avisar? não, instale à vontade sim, sempre

Por isso instalar extensão é livre e não causa conflito. Já npm install alguma-coisa mexe num arquivo que é de todo mundo — esse precisa de aviso no grupo antes.

As quatro recomendadas

ESLint todo mundo
Aponta erro de padrão enquanto você digita, com um risquinho embaixo do problema.
Por que importa
É exatamente a mesma checagem que roda quando você abre um Pull Request. Com a extensão, você vê o problema na hora e corrige; sem ela, descobre depois, quando a verificação automática reclamar e o seu PR ficar travado.
Prettier todo mundo
Arruma a formatação do arquivo sozinha — espaçamento, quebra de linha, aspas.
Por que importa
O projeto tem um padrão de formatação, e a verificação automática cobra ele. Além disso, formatação desalinhada polui o Pull Request: quem revisa perde tempo olhando mudança de espaço em vez de olhar o que você realmente fez.
Tailwind CSS IntelliSense Lara e Esther, principalmente
Completa os nomes das classes de estilo enquanto você escreve e mostra a cor de cada token num quadradinho ao lado.
Por que importa
No Estudia é proibido escrever cor na mão — só se usa os nomes prontos (text-magenta, border-gold…). Essa extensão mostra quais nomes existem e que cor cada um é, então você acerta sem precisar decorar a lista.
Error Lens quem está começando
Escreve o erro na própria linha, em vermelho, em vez de só sublinhar.
Por que importa
Sem ela, você precisa passar o mouse em cima do risquinho para ler a mensagem. Com ela, a mensagem já está na tela. Para quem está aprendendo TypeScript, isso economiza muito tempo.
Elas não substituem a conferência final
Antes de abrir o Pull Request, rode sempre os dois comandos: npx tsc --noEmit e npm run lint. As extensões só fazem você descobrir o problema mais cedo.

3.O dia a dia

Ao começar

git checkout main
git pull origin main
git checkout -b p3-erika/progresso-materia

O nome da branch segue o formato p<seu número>-<seu nome>/<o que faz>.

Enquanto trabalha

git add .
git commit -m "Mostra progresso da matéria em porcentagem"
Commit todo dia, mesmo inacabado
Trabalho não commitado é a única coisa que o Git não consegue recuperar. Se o notebook morrer, o que estava só na sua pasta se perde.

Ao terminar

git pull origin main
npx tsc --noEmit
npm run lint
git push -u origin p3-erika/progresso-materia

Depois abra o Pull Request no GitHub e mande o link no grupo.

Regras que valem para todos

1 Ninguém envia direto para a main. Tudo entra por Pull Request.
2 Nunca escreva cor na mão. Só os nomes prontos. Cor escrita na mão não muda junto com o tema.
3 Mexa só nos seus arquivos. A lista de cada pessoa está no repositório, em docs/DIVISAO-POR-PESSOA.md.
4 Pull Request pequeno. Um de 80 linhas passa na próxima janela de revisão; um de 800 fica para a seguinte.
5 Banco de dados: pare e chame a Esther. Ver a seção 5 deste guia.

4.Revisão: quando e como

A Esther aprova todos os Pull Requests. O GitHub pede a revisão dela automaticamente — você não precisa marcar ninguém.

Tudo que estiver aberto até a janela é revisado nela. O que chegar depois fica para a próxima. Não precisa cobrar — abra o PR, mande o link, e você já sabe quando terá resposta.

O que acontece

1. Você abre o Pull Request e manda o link no grupo 2. A verificação automática confere tipos e padrão de código 3. Na janela, a Esther revisa │ ┌────┴────┐ está ok? precisa mudar? │ │ aprova ela comenta o que mudar e mergeia │ VOCÊ corrige na sua branch │ volta na próxima janela
Quem corrige é quem escreveu
A Esther aponta o que precisa mudar, mas não mexe no seu código. O trabalho continua sendo seu e aparece como seu no histórico do projeto — o que importa, já que cada pessoa é avaliada pela própria contribuição.

Enquanto o seu PR espera, não pare

Crie a próxima branch a partir da branch atual e continue trabalhando:

git checkout -b p3-erika/proxima-parte

Quando o primeiro PR entrar, você atualiza a segunda com a main e segue. Assim a fila não vira tempo parado.

5.Banco de dados: pare e chame a Esther

Algumas tarefas precisam de uma coluna nova no banco. Quando chegar nessa hora, o seu roteiro mostra um aviso de PARE.

Por que essa regra existe

O grupo usa um único banco compartilhado. Se você errar num arquivo de código, quebra só a sua máquina e o Git desfaz. Se alguém aplicar um comando errado no banco, quebra para as seis pessoas ao mesmo tempo — e o Git não desfaz banco de dados.

Não é desconfiança. É o mesmo motivo pelo qual só uma pessoa mexe no disjuntor.

O que fazer

  1. Escreva o arquivo .sql com o nome já reservado para você — o conteúdo sugerido está no seu roteiro, é só copiar.
  2. Avise no grupo: "escrevi minha migration, pode aplicar?"
  3. A Esther confere, aplica e avisa quando estiver pronto.
  4. Você roda git pull e continua.
Não rode comando de banco por conta própria
Nada de supabase db push, nem mexer em tabela pelo painel do Supabase.
Você não fica parado esperando
Dá para adiantar quase tudo: montar a tela com dados de mentira escritos na mão, escrever a lógica de cálculo e filtro, e deixar o Pull Request quase pronto. Só o trecho que lê ou grava a coluna nova precisa esperar.

7.Deu problema?

O que aparece O que é O que fazer
Missing env vars falta o arquivo .env peça as chaves no grupo
column "..." does not exist alguém mudou o banco e você não atualizou git pull
Conflito ao dar git pull duas pessoas mexeram perto ver docs/CONFLITOS.md
O Pull Request ficou vermelho a verificação automática achou erro rode npx tsc --noEmit e npm run lint
npm install falha Node desatualizado instale a versão 20 ou mais nova
Conflito não é urgente, e nada foi perdido
O Git guarda as duas versões. Para desfazer e voltar ao ponto anterior: git merge --abort. Você volta exatamente para onde estava.

E chame alguém antes de tentar comandos novos. A maior parte dos trabalhos perdidos em projeto de faculdade acontece na tentativa de consertar sozinho, com comando copiado da internet.
